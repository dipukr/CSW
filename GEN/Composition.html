Composition

Composition is a stronger form of association where one object contains another object and the contained object cannot exist independently of the container.

The lifetime of the contained object depends on the lifetime of the container.

In composition if owning object is garbage collected the owned object will also be which is not the case in aggregation.

Composition means the child entity (order items) is part of a whole and cannot exist independently of the parent entity (order). The child entity is contained in the parent entity and can only be accessed via the parent entity.

Both composition and aggregation express a has-a relationship.

Composition expresses a strong has-a relationship (whole-part ownership).

Aggregation expresses a weak has-a relationship (association without ownership).

Both composition and inheritance used to solve the same problem that is code reuse.

Process of building complex objects from simpler ones is called object composition.

Use inheritance only when you want both hierarchical reuse of code and subtype polymorphism.

public class Room {
    private String name;
    public Room(String name) {this.name = name;}
}

public class House {
    House owns and creates its Rooms
    private List<Room> rooms = new ArrayList<>();

    public House() {
        rooms.add(new Room("Kitchen"));
        rooms.add(new Room("Bedroom"));
    }
}
How composition works

House creates its own Room objects internally.

The rooms belong to that house and are not shared.

When the house is garbage collected, its rooms go with it.

This models a strong part-of ownership relationship.

Composition in Java — Complete Guide with Code Examples

Composition is one of the most important principles in Object-Oriented Programming (OOP). It allows you to build complex objects by combining smaller, independent objects rather than inheriting their implementations.

The principle "Favor Composition Over Inheritance", popularized by the Gang of Four design patterns book, is fundamental to designing flexible, maintainable, testable software.

We will cover composition from basic Java examples through real-world designs, runtime behavior changes, design patterns, and Spring Boot.

1. What is composition?

Composition is an object-oriented design technique in which one object contains or uses other objects to provide its functionality.

Instead of inheriting behavior from a parent class, an object delegates work to the objects it contains.

Consider a Car and an Engine.

  • A car has an engine.
  • A car is not an engine.
  • A car delegates engine-related operations to its engine.

This is a HAS-A relationship.

Example 1: Basic composition

public class Engine {
    public void start() {
        System.out.println("Engine started");
    }

    public void stop() {
        System.out.println("Engine stopped");
    }
}

public class Car {
    private Engine engine = new Engine(); Car contains an Engine object

    public void start() {
        engine.start(); Delegation
        System.out.println("Car is moving");
    }

    public void stop() {
        engine.stop();
    }
}

public class Main {
    public static void main(String[] args) {
        Car car = new Car();
        car.start();
        car.stop();
    }
}

Output:

Engine started
Car is moving
Engine stopped

Notice what is happening:

  1. Car contains an Engine object.
  2. Car does not extend Engine.
  3. When car.start() is called, the Car delegates part of the operation to engine.start().
  4. Engine can have its own internal logic without exposing that implementation through Car’s API.

This is called delegation, a fundamental mechanism used in composition.

One subtle distinction: in strict UML terminology, composition implies ownership and a dependent lifecycle, whereas aggregation is a weaker whole–part relationship. In everyday Java design, the term composition is also widely used for collaborating objects supplied through constructors or setters, even when they have independent lifecycles.

2. Why choose composition over inheritance?

The biggest problem with inheritance is that it creates a fixed relationship between a child class and its parent implementation.

Inheritance works well for genuine subtype relationships, but becomes problematic when used only to reuse code.

Consider a notification system that supports:

  • Email and SMS delivery.
  • Plain-text and HTML formatting.
  • Different retry behaviors.

Let’s implement this first with inheritance, identify its limitations, and then redesign it using composition.

3. The problem with inheritance — practical example

Approach A: Using inheritance

Suppose we start with an abstract notification class.

public abstract class Notification {
    public abstract void send(String message);
}

public class EmailPlainNotification extends Notification {
    @Override
    public void send(String message) {
        System.out.println("Email: " + message);
    }
}

public class SmsPlainNotification extends Notification {
    @Override
    public void send(String message) {
        System.out.println("SMS: " + message);
    }
}

public class EmailBrandedNotification extends Notification {
    @Override
    public void send(String message) {
        System.out.println("Email: [ACME] " + message);
    }
}

public class SmsBrandedNotification extends Notification {
    @Override
    public void send(String message) {
        System.out.println("SMS: [ACME] " + message);
    }
}

Usage:

Notification notification = new EmailPlainNotification();
notification.send("Order shipped");

This works, but there are problems.

Problem 1: Subclass explosion

Suppose we support three delivery channels, three formatting strategies, and two retry policies.

Every additional dimension of behavior multiplies the potential combinations.

An inheritance hierarchy could use intermediate subclasses to share some code, but Java’s single class inheritance makes independently combining these dimensions awkward.

Problem 2: Tight coupling

If subclasses depend heavily on how the parent class works, changing the parent can break multiple subclasses.

For example, a parent may change the order in which overridable methods are called. A subclass that relies on the previous order may behave incorrectly, even though it still compiles.

This is known as the fragile base class problem.

Problem 3: Fixed inherited behavior

Consider:

Notification notification = new EmailPlainNotification();

The object’s runtime type is EmailPlainNotification. You cannot make that same object become an SmsBrandedNotification.

You can replace the reference with a different subclass instance, but you cannot independently replace the inherited behavior of the existing object.

With composition, you can change just the delivery channel or just the formatter.

Problem 4: Poor separation of responsibilities

Our notification subclasses are simultaneously responsible for deciding how to format a message and how to deliver it.

These responsibilities change for different reasons and should be independently configurable.

4. Redesign using composition

We can separate the notification system into three independent responsibilities.

The NotificationService now contains two collaborating objects:

public class NotificationService {
    private MessageSender sender;
    private MessageFormatter formatter;
}

The service no longer needs to know whether a message is sent through email or SMS, or whether a message is formatted as plain text or branded text.

It only knows the interfaces.

public interface MessageSender {
    void send(String destination, String message);

public class EmailSender implements MessageSender {
    @Override
    public void send(String destination, String message) {
        System.out.println("EMAIL to " + destination + ": " + message);
    }
}

public class SmsSender implements MessageSender {
    @Override
    public void send(String destination, String message) {
        System.out.println("SMS to " + destination + ": " + message);
    }
}

2. Formatting behavior
============================================

public interface MessageFormatter {
    String format(String message);
}

public class PlainTextFormatter implements MessageFormatter {
    @Override
    public String format(String message) {
        return message;
    }
}

public class BrandedFormatter implements MessageFormatter {
    private String brand;

    public BrandedFormatter(String brand) {
        this.brand = brand;
    }

    @Override
    public String format(String message) {
        return "[" + brand + "] " + message;
    }
}

3. Composition
============================================

public class NotificationService {
    private MessageSender sender;
    private MessageFormatter formatter;

    public NotificationService(MessageSender sender, MessageFormatter formatter) {
        this.sender = Objects.requireNonNull(sender);
        this.formatter = Objects.requireNonNull(formatter);
    }

    public void sendNotification(String destination, String message) {
        String formatted = formatter.format(message); Step 1: Delegate formatting
        sender.send(destination, formatted); Step 2: Delegate delivery
    }

    public void setSender(MessageSender sender) {
        this.sender = Objects.requireNonNull(sender);
    }

    public void setFormatter(MessageFormatter formatter) {
        this.formatter = Objects.requireNonNull(formatter);
    }
}

5. Composition can be immutable or runtime-configurable

An important distinction: composition does not require mutable fields or setter methods.

Immutable composition — usually preferred

public final class NotificationService {
    private MessageSender sender;
    private MessageFormatter formatter;

    public NotificationService(MessageSender sender, MessageFormatter formatter) {
        this.sender = Objects.requireNonNull(sender);
        this.formatter = Objects.requireNonNull(formatter);
    }

    public void sendNotification(String destination, String message) {
        sender.send(destination, formatter.format(message));
    }
}

Here, dependencies are supplied through the constructor and cannot be reassigned.

NotificationService emailService = new NotificationService(new EmailSender(), new PlainTextFormatter());
NotificationService smsService = new NotificationService(new SmsSender(), new BrandedFormatter("ACME"));

Each service has its own behavior configuration. This approach is often easier to reason about, especially when objects are shared across threads.

Runtime selection without modifying a shared object

In a multithreaded application, changing a singleton service’s sender using setters can create race conditions.

A safer approach is to select an appropriate sender for each request.

public enum Channel {
    EMAIL, SMS
}

public class NotificationRouter {
    private Map<Channel, MessageSender> senders;

    public NotificationRouter() {
        senders = Map.of(Channel.EMAIL, new EmailSender(), Channel.SMS, new SmsSender());
    }

    public void send(Channel channel, String destination, String message) {
        MessageSender sender = senders.get(channel);
        if (sender == null) {
            throw new IllegalArgumentException("Unsupported channel: " + channel);
        }
        sender.send(destination, message);
    }
}

Usage:

NotificationRouter router = new NotificationRouter();
router.send(Channel.EMAIL, "alice@example.com", "Hello");
router.send(Channel.SMS, "+919876543210", "Hello");

The router remains the same object, but independently composed sender objects determine the behavior of each request. This design avoids mutating the router’s shared configuration.

6. Composition and the Strategy design pattern

Composition is a general OOP technique. Strategy is a design pattern that uses composition to make interchangeable algorithms possible.

Consider a payment system.

public interface PaymentStrategy {
    void pay(double amount);
}

public class CardPayment implements PaymentStrategy {
    @Override
    public void pay(double amount) {
        System.out.println("Paying by card: " + amount);
    }
}

public class UpiPayment implements PaymentStrategy {
    @Override
    public void pay(double amount) {
        System.out.println("Paying by UPI: " + amount);
    }
}

Now build a Checkout object using composition.

public class Checkout {
    private PaymentStrategy paymentStrategy;

    public Checkout(PaymentStrategy paymentStrategy) {
        this.paymentStrategy = paymentStrategy;
    }

    public void changePaymentMethod(PaymentStrategy paymentStrategy) {
        this.paymentStrategy = paymentStrategy;
    }

    public void placeOrder(double amount) {
        paymentStrategy.pay(amount);
    }
}

Usage:

Checkout checkout = new Checkout(new CardPayment());
checkout.placeOrder(1000);
checkout.changePaymentMethod(new UpiPayment()); Change behavior at runtime
checkout.placeOrder(2000);

Output:

Paying by card: 1000.0
Paying by UPI: 2000.0

The Checkout class does not implement card or UPI payment algorithms. It composes a PaymentStrategy, and the chosen strategy performs the work.

For financial applications, use BigDecimal or an appropriate money type instead of double; the example above uses double only to keep the design demonstration short.

7. Composition with the Decorator pattern

Composition also enables us to add functionality around existing implementations without modifying them.

Suppose every notification must be logged.

With inheritance, we might create LoggingEmailSender, LoggingSmsSender, and more subclasses for every existing sender.

With composition, one reusable wrapper is enough.

public class LoggingSender implements MessageSender {
    private MessageSender delegate;

    public LoggingSender(MessageSender delegate) {
        this.delegate = delegate;
    }

    @Override
    public void send(String destination, String message) {
        System.out.println("Sending notification...");
        delegate.send(destination, message);
        System.out.println("Send operation completed");
    }
}

Usage:

MessageSender email = new LoggingSender(new EmailSender());
MessageSender sms = new LoggingSender(new SmsSender());
email.send("alice@example.com", "Welcome");
sms.send("+919876543210", "Welcome");

This is the Decorator design pattern.

The decorator implements the same interface as the object it wraps. Because both share an interface, the decorator can be added without modifying the original sender implementation.

We can even compose multiple decorators:

MessageSender sender = new LoggingSender(new LoggingSender(new EmailSender()));

In practice, each wrapper would provide a distinct behavior, such as metrics, validation, or retry policies. Retrying a delivery operation requires care because repeating an operation that already succeeded can cause duplicate messages.

8. Composition improves unit testing

This is one of the biggest advantages in production applications.

Suppose we want to test that NotificationService formats messages correctly. We should not need to send a real email or SMS.

We can replace the sender with a fake implementation.

public class FakeSender implements MessageSender {
    String lastDestination;
    String lastMessage;

    @Override
    public void send(String destination, String message) {
        lastDestination = destination;
        lastMessage = message;
    }
}

JUnit 5 test:

public class NotificationServiceTest {
    @Test
    void shouldFormatMessageBeforeSending() {
        FakeSender fakeSender = new FakeSender();
        NotificationService service = new NotificationService(fakeSender, new BrandedFormatter("ACME"));
        service.sendNotification("alice@example.com", "Order shipped");
        assertEquals("alice@example.com", fakeSender.lastDestination);
        assertEquals("[ACME] Order shipped", fakeSender.lastMessage);
    }
}

The test doesn’t need a network connection, SMTP server, or SMS gateway.

Composition makes this straightforward because the service depends on an abstraction (MessageSender), not a concrete delivery mechanism. Inheritance can also support test doubles, but interface-based composition usually gives each component a smaller and more focused testing contract.

9. Composition in Spring Boot

Spring Boot relies heavily on composition and dependency injection.

Let’s build a checkout service that delegates payment processing to a separate component.

Step 1: Define an interface

public interface PaymentGateway {
    void charge(BigDecimal amount);
}

Step 2: Implement different gateways

@Component("cardGateway")
public class CardPaymentGateway implements PaymentGateway {
    @Override
    public void charge(BigDecimal amount) {
        System.out.println("Card payment: " + amount);
    }
}
@Component("upiGateway")
public class UpiPaymentGateway implements PaymentGateway {
    @Override
    public void charge(BigDecimal amount) {
        System.out.println("UPI payment: " + amount);
    }
}

These are illustrative payment implementations, not real integrations with a payment provider.

Step 3: Compose the service using constructor injection

@Service
public class CheckoutService {
    private PaymentGateway paymentGateway;

    public CheckoutService(@Qualifier("cardGateway") PaymentGateway paymentGateway) {
        this.paymentGateway = paymentGateway;
    }

    public void checkout(BigDecimal amount) {
        paymentGateway.charge(amount);
    }
}

Spring injects the CardPaymentGateway into CheckoutService.

If the application needs a different implementation, we can change the injection configuration without changing CheckoutService’s business logic.

This demonstrates the relationship between three important concepts:

ConceptMeaning
CompositionCheckoutService contains a PaymentGateway reference
Dependency InjectionSpring supplies the appropriate gateway object
Dependency Inversion PrincipleHigh-level checkout logic depends on the PaymentGateway abstraction

These concepts complement each other, but are not identical.

Composition does not require Spring. The same design works with ordinary Java constructors, as shown in the earlier examples.

When inheritance violates substitutability

Inheritance should respect the Liskov Substitution Principle (LSP): a subtype should be usable wherever its parent type is expected without violating the parent’s behavioral contract.

Consider this classic example:

public class Bird {
    void fly() {
        System.out.println("Flying");
    }
}

public class Penguin extends Bird {
    @Override
    void fly() {
        throw new UnsupportedOperationException("Penguins cannot fly");
    }
}

A function that accepts a Bird and assumes fly() will work fails for a Penguin.

The problem is not that a penguin isn’t a bird. The problem is that the base class incorrectly assumes every bird has a flying behavior.

A better model separates the capability.

public interface Movement {
    void move();
}

public class Flying implements Movement {
    public void move() {
        System.out.println("Flying");
    }
}

public class Walking implements Movement {
    public void move() {
        System.out.println("Walking");
    }
}

public class Bird {
    private Movement movement;

    Bird(Movement movement) {
        this.movement = movement;
    }

    void move() {
        movement.move();
    }
}

Usage:

Bird eagle = new Bird(new Flying());
Bird penguin = new Bird(new Walking());
eagle.move(); Flying
penguin.move(); Walking

The key improvement is that movement is modeled as an independently variable capability rather than an assumption embedded in every bird subtype.

This is particularly useful when behavior is shared across otherwise unrelated classes.

11. When should you actually use inheritance?

"Favor composition over inheritance" does not mean inheritance is bad or should never be used.

Inheritance remains appropriate when there is a genuine, stable subtype relationship and a clear behavioral contract.

For example:

public abstract class Shape {
    public abstract double area();
}

public class Circle extends Shape {
    private double radius;

    public Circle(double radius) {
        this.radius = radius;
    }

    @Override
    public double area() {
        return Math.PI * radius * radius;
    }
}

public class Rectangle extends Shape {
    private double width;
    private double height;

    public Rectangle(double width, double height) {
        this.width = width;
        this.height = height;
    }

    @Override
    public double area() {
        return width * height;
    }
}

Here, Circle and Rectangle are both shapes, and both honor the area() contract.

Inheritance is reasonable because the types are genuine specializations with a consistent abstraction.

Even here, Java interfaces could also express the common capability. The choice between an interface and an abstract base class depends on whether shared implementation or state is genuinely useful.

12. How to choose between composition and inheritance

Use this decision guide when designing Java classes.

A practical rule is to ask two questions before writing extends:

1. Is the new class truly a specialized version of the parent? If not, composition is probably a better fit.

2. Am I inheriting only because I want to reuse a few methods? If so, consider extracting those methods into a separate collaborator instead.

Also avoid composition overengineering. A separate interface and class for every one-line operation can make a simple system harder to understand. Extract behaviors that represent meaningful responsibilities or realistic variation points.

14. Final takeaway

The goal of composition is not simply to avoid the extends keyword.

Its real value is to separate responsibilities, isolate changes, and assemble behavior from independent components.

Think of it this way:

Inheritance:
"I want to become a specialized version of you."
public class Child extends Parent {}

Composition:
"I want to use your capability."
public class Service {
    private Capability capability;

    Service(Capability capability) {
        this.capability = capability;
    }
}

When a system has behaviors that evolve independently—payment processing, notification delivery, caching, validation, persistence, retry logic, or formatting—composition generally leads to a design that is easier to extend and test.

The central principle: Inherit a type only when the subtype relationship is genuinely valid. Compose objects when you want to reuse or vary behavior.
